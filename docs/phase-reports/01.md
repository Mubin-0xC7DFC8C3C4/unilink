### 3.2 Shape

- **Modular monolith.** One Spring Boot deployable, one MySQL 8 schema, one React + TypeScript frontend with two entry points (D-001, D-002, D-005).
- **Single origin.** Nginx terminates HTTPS and serves `/` (student SPA), `/admin` (admin SPA), `/api/**` and `/ws/**` (Spring Boot). No CORS needed (empty allow-list).
- **Server-side sessions** in MySQL (Spring Session JDBC), cookie `UL_SESSION` (D-013). No JWT in browsers. No Redis / broker / search engine in v1.0 (D-003).
- **Provider adapters in-process** behind interfaces, so a provider or a separate service can replace them without touching callers.
- **Backend package structure** as in `ARCHITECTURE_OVERVIEW.md` §3 (feature-first: `common`, `config`, `security`, `identity`, `profile`, `community`, `content`, `event`, `team`, `messaging`, `search`, `moderation`, `notification`, `admin`, `audit`, `storage`, `integration/`).
- **Frontend structure** as in `ARCHITECTURE_OVERVIEW.md` §4 (`app/`, `design/`, `api/`, `features/`, `admin/`, `i18n/`, `test/`).

### 3.3 Security architecture (proposal, to be implemented and tested in Phases 5, 9 and 10)

- Two Spring Security filter chains: `@Order(1)` for `/api/admin/**` and `/admin/**`, authenticating only `AdminPrincipal` and requiring `MFA_VERIFIED`; `@Order(2)` for everything else with `UnilinkUserPrincipal`. A student principal can never satisfy the admin chain (different type, different table, D-030).
- `AccessPolicy` is the single decision point; services call it; repositories apply university scope in the query; out-of-scope resources return 404.
- Every student write path also requires state `VERIFIED` (FR-AUTH-13, TC-07).
- Password hashing Argon2id (D-014); student password rule 8+ characters with upper, lower and digit; admin 12+ characters (D-031).
- CSRF on (double-submit cookie), security headers (HSTS, CSP `default-src 'self'`, nosniff, Referrer-Policy, Permissions-Policy, frame denial), login throttling / lockout, OTP expiry / attempts / cooldown / caps, rate limits on OTP / login / reset / upload / message / report.
- Upload validation (size, Tika content sniffing, re-encode, random keys, private storage); ID card private storage with authorised streaming only.
- WebSocket: HTTP session authenticates STOMP CONNECT; `ChannelInterceptor` authorises every SUBSCRIBE and SEND against room membership, block lists and account state.
- Audit: every admin mutation and admin login outcome written through `AuditService` in the same transaction as the change, with actor, action, target type / id, reason, metadata (no personal data beyond ids), IP and timestamp, chained by hash; no update / delete API; runtime DB user has `INSERT, SELECT` only on `audit_logs`; trigger rejects UPDATE / DELETE (D-037).

## 6. Security-sensitive defaults — Phase 1 review (not finalised)

### 6.1 Phone uniqueness (D-011 / D-067) — OPEN

**Why it matters:** phone verification is part of account identity (FR-AUTH-04 / FR-AUTH-07). If one phone can verify many accounts, a single SIM can create multiple verified identities, weakening the "verified student" guarantee and enabling duplicate / Sybil accounts, duplicate OTP abuse, and evasion of suspension by re-registering. If phone uniqueness is enforced strictly, legitimate cases are blocked: shared family phones, students without a personal phone, SIM recycling in Bangladesh (a number reassigned to a new person), and students who change numbers.

**What the log said:** D-011 default was "do not enforce phone uniqueness, rate-limit per phone, flag duplicates to reviewers". That default was a proposal, not a security decision.

**Phase 1 position:** no final decision. Options for the owner (see §9, Q3):
(a) enforce unique phone per account; (b) keep the D-011 default (non-unique, rate-limited, reviewer flag); (c) unique per university; (d) soft uniqueness — allow, but require manual review when a phone is already used, and block a phone that is already attached to a suspended / banned account.

Phase 1 recommends the owner also decide: what happens on number change, whether a phone attached to a deleted account can be reused, and whether OTP rate limits are per phone, per IP, or both (NFR-SEC-05). This must be decided before Phase 5 (authentication / verification).

### 6.2 Admin TOTP 2FA and recovery (D-031 / D-068) — PROPOSED, recovery OPEN

**What the log said:** TOTP (RFC 6238), enrolled at first login, 10 single-use hashed recovery codes, email OTP fallback, admin password ≥12 characters, idle timeout 30 minutes, optional IP allow-list, separate throttling / lockout.

**Phase 1 secure-design requirements (to be approved before Phase 5 / 9):**
- TOTP secrets encrypted at rest (`ENCRYPTION_KEY`), never in logs or responses; enrolment only after password authentication, with a confirmation code before the secret is activated.
- Recovery codes hashed (like passwords), single-use, regeneration invalidates all prior codes, use is audited and notified.
- Email OTP fallback must not silently weaken 2FA: short expiry, single use, rate-limited, audited, and its use should be visible to a Platform Admin. Whether email OTP alone should ever satisfy the second factor for a Platform Admin is an owner decision — see §9, Q4.
- Lost-authenticator recovery must NOT be self-service password-reset style. Proposed: Platform Admin-initiated reset after identity verification, with audit, session revocation, and re-enrolment. No recovery path may bypass the admin chain.
- Bootstrap of the first Platform Admin must be a documented, one-time, environment-variable command (Master Guide §6), with forced password rotation and TOTP enrolment at first login. No public admin registration endpoint, ever.
- Admin login, 2FA and failed attempts have their own throttling / lockout, separate from student login. Failed logins for an existing admin account are audit-logged (TC-23); failures for unknown emails go to the application security log only (D-037).

No TOTP implementation was written in Phase 1.

### 6.3 Auto-hide (D-034 / D-069) — PROPOSED, pending SRS verification

**Required safeguards (Phase 1 review, to be confirmed against the SRS):**
- Threshold: 5 **distinct verified** reporters. Reporter must be verified, not the owner, and have one active report per target. Duplicate reports by the same reporter do not count.
- Duplicate prevention: unique constraint on `reports(reporter_id, target_type, target_id)` where active, plus an idempotency / concurrency guard so simultaneous 5th and 6th reports hide exactly once (TEST_STRATEGY §4).
- Abuse safeguards: rate limit on reports (NFR-SEC-05), flood detection, and a reviewer-visible report history. Brigading is a known risk: 5 coordinated reporters can hide legitimate content. The mitigation in the documents is the appeal path + admin review + strike / audit trail, not a change to the threshold in Phase 1. Whether any additional safeguard (for example, a higher threshold for certain content, or a cooling-off review) is wanted is an owner question — see §9, Q5.
- Scope: auto-hide for posts, events and comments only. Profiles and messages are flagged high priority, not auto-hidden (D-034).
- Appeal: owner can appeal a hidden item (FR-REP-03); appeal appears in the admin queue; admin decision (restore / keep hidden / remove / request edit) is audited, and the owner is notified.
- Strikes: 3 auto-hides in 30 days flags the user for admin review and may restrict posting (FR-REP-04). Threshold, window and strike rule are rows in `system_settings`, editable only by Platform Admin and audited.
- Audit: every auto-hide transition, appeal and admin decision writes an audit / moderation event in the same transaction as the change where the documents require it.

The threshold value (5), the window, and the 3-in-30-days rule must be checked against the SRS on receipt (D-071). If the SRS says something different, the SRS wins.

- **WCAG AA:** all essential text, interactive elements, status indicators and focus states must meet WCAG 2.1 AA contrast (4.5:1 for normal text). `text-muted` at 3.35:1 (light) and 3.85:1 (dark) on background, as reported by the `DESIGN.md` linter in the document itself, is below AA and must NOT be used for information a user needs to act on. ## 7. Security risk assessment (Phase 1)

Severity is a Phase 1 judgement based on the documents, not on tested code (no code exists yet). "Likelihood" is exposure if the control is missed, not a measured rate.

| # | Risk | Severity | What the documents require | Phase 1 note |
|---|---|---|---|---|
| R-01 | Student-to-admin privilege escalation | High | Separate `admin_accounts`, separate filter chain, separate principal type, `MFA_VERIFIED` (D-030, §6) | Structurally prevented by design, but only if the two chains, the principal types and the `/api/admin/**` namespace are implemented exactly as specified. The AuthZ matrix test must enumerate every route or the build fails. Mass-assignment (`role`, `status`, `verified` in profile updates) must be ignored and tested. |
| R-02 | Moderator cross-university access (IDOR / scope leak) | High | Scope in repository queries, 404 not 403, moderator isolation suite (D-032, TC-26) | Hiding buttons is not security. Every admin query, count, search, audit read and ID-image stream must be scoped. A single unscoped query leaks another university's students, content or reports. |
| R-03 | ID card image disclosure | High | Private storage, authorised streaming, 60-second signed URL, no URL in logs / list responses (NFR-SEC-04, D-053) | Images are the most sensitive student data in the system. Any list response, log line, error message or cached URL that exposes an ID image is a breach of the design. Owner / in-scope reviewer only. |
| R-04 | OTP / login brute force and SMS abuse | High | OTP 6 digits, 5 min, 5 attempts, hashed, single use, resend cooldown, per-phone / per-IP caps; login lock 15 min after 5 failures; generic errors, no user enumeration (D-011, FR-AUTH-10, NFR-SEC-05) | SMS sending is a cost and abuse vector. Rate limits must be enforced server-side and at the Nginx edge, not only in the UI. |
| R-05 | Auto-hide brigading / false reporting | Medium–High | 5 distinct verified reporters, duplicate prevention, appeal, audit (D-034, D-069) | 5 coordinated reporters can hide legitimate content. Appeal + admin review is the mitigation in the documents. No additional safeguard was decided in Phase 1 — see Q5. |
| R-06 | Phone identity weakness (duplicate / Sybil accounts) | Medium–High | See §6.1 (D-067) | Unresolved. The decision directly affects the strength of "verified student". |
| R-07 | Admin 2FA bypass via recovery / fallback | High | See §6.2 (D-068) | Email OTP fallback and lost-authenticator recovery are the weakest points in the admin chain if designed loosely. Must be approved before implementation. |
| R-08 | Audit log tampering / missing audit rows | High | Append-only, hash chain, trigger, DB grants, same-transaction write (D-037) | If an admin action writes without its audit row, or the runtime DB user can update `audit_logs`, the accountability guarantee fails. Tested by asserting the DB row and the audit row together. |
| R-09 | WebSocket unauthorised subscribe / send | Medium–High | Session-authenticated CONNECT, `ChannelInterceptor` per SUBSCRIBE / SEND, room membership + block checks (ARCH §6) | A room topic that does not check membership leaks private / team messages. Session must be dropped on logout, suspension or password change. |
| R-10 | XSS / SQL injection via user content | Medium–High | Parameterised JPA, allow-listed sort fields, text rendering, sanitiser for any rich text, CSP, `javascript:` / `data:` URL rejection (NFR-SEC-02, TC-20) | Bangla text, links, filenames and chat messages are all injection surfaces. Playwright must check no script executes. |
| R-11 | Insecure file upload (polyglot, SVG, path traversal, EXIF) | Medium | Size limits, Tika sniffing, allow-listed types, re-encode, random keys, private bucket, EXIF stripping (D-029a, TEST_STRATEGY §5) | Extension checks alone are insufficient. Content sniffing + re-encoding + private storage are required. |
| R-12 | Session fixation / session not invalidated | Medium | New session id on login, invalidate on logout / password change / suspension / ban / revocation, idle timeouts 2h student / 30 min admin (D-013, D-031) | All of a user's sessions must be deleted on password change, suspension, ban and verification revocation. A second browser session must die — tested, not asserted. |
| R-13 | Account deletion vs retention conflict | Medium | Anonymise-and-delete, messages remain as "Deleted user", audit keeps numeric id only, backups age out in 14 days (D-052) | Legal review against applicable Bangladeshi data-protection rules is required before launch (D-052). This log does not claim legal compliance. |
| R-14 | OCR / SMS / email provider outage causes data loss or duplicate work | Medium | Async OCR with retry + backoff, OCR failure never blocks the queue, outbox / `AFTER_COMMIT` + idempotency keys, bounded executor (Master Guide §8, NFR-FLT-02/03) | A provider outage must not lose or duplicate verification work. Fakes live only in `test` / `e2e` profiles. |
| R-15 | Performance / availability claimed without measurement | Medium | p95 targets, k6, 100,000-row search benchmark, hardware must be stated (D-050) | No performance target may be reported as met without a test run. NFR-AVL-01 (99% monthly) needs a month of monitoring data. |
| R-16 | Design contrast failure for essential text | Medium | WCAG 2.1 AA, `text-muted` limited to non-essential captions (D-040, D-070) | If muted text is used for status, errors or actions, users will miss essential information. This is an accessibility defect, not a cosmetic one. |
| R-17 | Secrets in repository / logs | Medium | Environment variables only, `.env.example`, never log passwords / OTPs / tokens / ID URLs (Master Guide §1, §9) | Secret scanning in CI, log scanning for OTP / password / token values in tests. |
| R-18 | Single-instance scaling limits | Low–Medium for v1.0 | In-memory STOMP broker, in-process rate limiter, session in DB (D-003, D-051) | Acceptable for v1.0 single instance. A second instance requires an external STOMP relay / pub-sub and a shared rate limiter — at that point Redis becomes justified, with a decision-log entry. |
